## Software Beyond Code and the Best-of-Breed Tool Trade-off

**Q: Given that software >> code, name at least 3 other things that are important in software that aren't directly code. The Professor mentioned using less tools rather than more tools. Argue why it might be good to use so-called "best of breed" tools for each thing you want to do. Now argue how that can be inefficient and what effects more tools might have on teams.**

Software is far more than its source code. At minimum, three other critical artifacts and systems constitute a working software product: **requirements and specifications** (user stories, acceptance criteria, formal specs) that define what the system must do and serve as the contract between engineering and stakeholders; **automated test suites** that verify the system behaves correctly and serve as executable documentation of intended behavior; and **deployment and infrastructure configuration** (CI/CD pipelines, Dockerfiles, Kubernetes manifests, Terraform definitions) that encode how software is built, delivered, and kept running — because a correct application deployed incorrectly is still a broken system. Runbooks, API documentation, and architectural diagrams round out the picture of everything that must be maintained alongside code.

**The case for best-of-breed tools:** Each specialized tool is optimized for its specific problem. A purpose-built formatter like Prettier, a purpose-built test runner like Jest, and a purpose-built CI system like GitHub Actions each offer deeper feature sets, larger communities, more frequent updates aligned to their domain, and tighter integration with the ecosystem around them than any generalist tool attempting to do everything. When something goes wrong, there is extensive documentation, StackOverflow coverage, and community support specific to that tool's problem space. Specialists solve specific problems better than generalists — this applies to software tools as much as to human professionals.

**The case against (the Professor's position):** More tools means more onboarding cost: every new team member must learn the configuration, quirks, and failure modes of each tool in the stack. More tools means more integration surface — each point where Tool A produces output that Tool B consumes is a potential compatibility failure that someone must detect, debug, and maintain. Cognitive load compounds: switching mental contexts between 12 different tools throughout a workday fragments focus and introduces friction that accumulates invisibly. There is also a version compatibility problem: tools evolve independently, and keeping a large toolchain in sync across major version upgrades is itself a significant ongoing engineering cost. In small teams especially, the overhead of owning a "best of breed" ecosystem frequently exceeds the marginal quality benefit each individual tool provides over a simpler alternative. A team that spends 20% of its time on toolchain maintenance is not spending that time on the product — and toolchain complexity, like code complexity, tends to grow monotonically once introduced.

## Plans and Diagrams That Stay Current

**Q: The idea of having plans and diagrams that describe your software seems like a good idea, but unfortunately such things seem to go out of date very quickly. Explain why this is the case and propose a solution to this problem. Hint: Think about how JSDocs works for comments and what you might do.**

Plans and diagrams go out of date because they are static artifacts maintained by humans in a dynamic process, with no automated mechanism to detect or penalize drift. The moment implementation diverges from a diagram — which happens on day one of any real project — the diagram begins its slide toward inaccuracy. Unlike code (which must compile) or tests (which must pass in CI), diagrams have no hard feedback loop: nothing fails when a sequence diagram no longer reflects how two services actually communicate. The update cost feels optional, so it is perpetually deferred in favor of work that has immediate, visible consequences. This is rational individual behavior that produces collectively irrational outcomes — a codebase full of diagrams that are worse than no diagrams because they actively mislead.

The JSDocs insight is the key to the solution: documentation that lives immediately adjacent to the thing it describes, maintained in the same edit-and-commit workflow, is far more likely to stay current than documentation that lives in a separate system. JSDocs are reviewed as part of the PR, fail linting when malformed, and are owned by the same engineer who owns the code — the natural friction of the development workflow keeps them close to correct. Applied to architectural diagrams: **treat diagrams as code in the repository.** Tools like Mermaid, PlantUML, and Structurizr DSL allow diagrams to be authored as text files, committed to version control, and rendered from the source — when the implementation changes in a PR, the same PR must update the diagram file or it is visibly incomplete to reviewers. The diagram is no longer a separate artifact maintained by a separate process; it is subject to the same review discipline as the code.

Going further: **derive diagrams from the system rather than describing it.** API documentation generated automatically from OpenAPI/JSDoc annotations always reflects the current API surface. Service dependency graphs generated from observability tooling or static import analysis reflect actual dependencies, not remembered ones. When diagrams are measurements of the system rather than human opinions about it, staleness becomes structurally impossible rather than merely discouraged. The combination — co-located diagram-as-code for architectural intent, auto-generated documentation for implementation details — covers the space that neither approach handles alone.

## Enforcing Code Style When Humans Won't

**Q: It is encouraged that all code in a repo should be written as if done by one "common" person for the team. Explain why you should stop arguing about tabs vs. spaces and just settle for some decision. While this appears to have worked, one of the "space fanatics" simply won't adhere to the guideline — what can we do to keep our non-conformer from spoiling the repo?**

The tabs-vs-spaces debate is a textbook bikeshedding problem: the decision is low-stakes, there is no objectively correct answer, and precisely because the stakes are low, everyone feels entitled to a strong opinion. The cost of the argument — team friction, delayed momentum, a codebase in inconsistent limbo during the standoff — vastly exceeds the cost of any specific resolution. The fundamental insight is that **consistency matters far more than the choice itself.** A team that uniformly uses tabs produces more maintainable code than a team half of whom use tabs and half spaces, regardless of which convention is objectively more elegant. Mixed style creates cognitive friction in every code review, makes `git blame` and diff output noisy, and signals to readers that the team does not have shared ownership of the codebase's quality. Pick anything reasonable, document it, and move — the time spent arguing is the only real waste.

For the non-conformer: the right solution is to remove the human decision from the loop entirely, because a social problem with a technical solution should always be solved technically. Three layers of enforcement:

**1. Auto-formatting on save / pre-commit:** A formatter like Prettier (for JS/CSS/HTML) or an EditorConfig file ensures that code is reformatted to the agreed style automatically before it is ever committed. A pre-commit hook via Husky runs the formatter on staged files at `git commit` time — the non-conformer's code is silently corrected before it enters the repo, without requiring any confrontation.

**2. CI lint check:** A linting step in the CI pipeline (ESLint, Stylelint, or a format-check script) rejects any PR that contains style violations. This provides a hard technical gate: non-conforming code cannot merge, regardless of what the individual developer does locally. The enforcer is the build system, not a teammate.

**3. EditorConfig in the repo root:** An `.editorconfig` file that most editors respect automatically configures indentation, end-of-line characters, and trailing whitespace for anyone who opens the project — reducing the non-conformer's ability to accidentally violate the style even if they wanted to follow it. The repo itself nudges every editor toward compliance.

The broader principle is that style standards that rely on individual discipline and social pressure will always have non-conformers. Style standards enforced mechanically by the toolchain are effectively unconditional — and they remove the psychological burden of colleagues policing each other, which is itself a source of team friction worth eliminating.
