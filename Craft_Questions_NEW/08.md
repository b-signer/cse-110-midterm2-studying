## The -ilities: Quality Attributes and Their Application

**Q: Make sure you are aware of all the -ilities (17 with 8 key ones). Be prepared to discuss design decisions or examine code and relate which -ility should be considered. Know how you could verify conformance, consider HTML/CSS/JS examples, and be able to convert a vague requirement into a concrete one.**

The -ilities are the non-functional quality attributes that describe *how* a system behaves rather than *what* it does. Following the **ISO 25010 Software Quality Model**, the **8 key ones** are: **Functional Suitability** (the system provides functions that meet stated and implied needs), **Performance Efficiency** (resource usage, throughput, and response time), **Compatibility** (works correctly across different browsers, devices, and environments), **Usability** (how effectively and intuitively users can interact with it), **Reliability** (the system produces correct results consistently over time), **Security** (resistance to unauthorized access, manipulation, or data disclosure), **Maintainability** (how easily the system can be changed, extended, or debugged), and **Portability** (ability to operate in different environments or platforms). Additional -ilities include: Availability, Robustness, Accessibility, Testability, Scalability, Interoperability, Flexibility, Reusability, Durability, Installability, and Modifiability — rounding out the 17.

**Verifying conformance:** Reliability → measure uptime percentages and Mean Time Between Failures (MTBF) in production. Maintainability → track cyclomatic complexity and time-to-change for standard bug fixes. Usability → task completion rates and error rates from usability testing sessions. Performance → load test at target concurrency and measure 95th-percentile response times. Security → run OWASP ZAP scans, static analysis (ESLint security plugins), and penetration tests. Scalability → horizontal scaling tests measuring throughput per additional instance.

**HTML/CSS/JS -ility examples:**
- `<link rel="stylesheet" href="http://example.org/themes/cool.css">` — **Reliability**: if example.org is unavailable, your page has no styles at all. **Performance**: the external stylesheet is render-blocking and adds a full network round-trip. **Security**: `http` (not `https`) exposes this resource to man-in-the-middle CSS injection; any external resource is a supply-chain attack surface. **Robustness**: there is no fallback if the stylesheet returns a 404.
- `<img src="photo.jpg">` with no `alt` attribute — **Usability/Accessibility**: screen readers have nothing to announce; the image is invisible to assistive technology users.
- `<script src="analytics.js">` without `defer` or `async` — **Performance**: blocks HTML parsing until the script is fetched and executed, increasing page load time.
- `<input type="text" name="telephone">` instead of `type="tel"` — **Usability**: misses the numeric soft keyboard on mobile devices and loses browser-level semantic validation.

**Vague → Specific requirement example:**
- **Vague:** "The app should be fast."
- **Specific:** "The product search results page shall return a rendered response within 2 seconds for 95% of requests under a concurrent load of 500 users, measured at the 95th-percentile response time in the production environment using realistic query distributions."

The specificity provides a measurable acceptance criterion — you can now write a load test that either passes or fails, rather than debating subjectively whether the app "feels fast enough."

## Vague Requirements and What Humans Offer That LLMs Cannot

**Q: Prompting an LLM with a vague prompt seems like it gives you random results. Would the same happen if a stakeholder gave you a vague prompt? What can you do as a human software engineer that LLMs seem unable to really offer?**

A vague stakeholder brief ("we need a better user experience") and a vague LLM prompt ("make a login page") produce similarly unpredictable outputs — both fill ambiguity with assumptions, and those assumptions may be wrong. The difference is what happens next. An LLM silently generates something that looks complete, presenting a confident artifact with no signal that critical decisions were made arbitrarily. A human software engineer has the professional obligation and interpersonal capacity to push back: to ask "what do you mean by better — faster, simpler, more consistent with your brand, more accessible to users with disabilities?" and to keep asking until the requirement becomes testable.

The deeper capability gap is that requirements engineering is fundamentally relational and contextual, and LLMs cannot participate in that relationship. A human engineer can read an organization's political dynamics to understand why a requirement is worded a particular way — e.g., that "the manager wants a dashboard" is really a proxy for "the manager is frustrated that they can't answer questions in board meetings without waiting for a data analyst." They can identify contradictions between stakeholders, notice when a stated requirement conflicts with a business constraint nobody mentioned, and escalate ambiguity to the right decision-maker. They can interpret silence: a stakeholder who doesn't respond to a clarifying question is telling you something. They can translate business language into technical constraints while preserving the intent, and can propose alternative framings when the original requirement is technically impossible or disproportionately expensive. LLMs can generate text plausibly resembling requirements; they cannot discover, negotiate, or validate the actual requirements that govern whether the software solves the actual problem.

## Why Architectural Notation Isn't Standard Practice

**Q: Why do you think that software systems and architectural diagrams and their notational form are not standard practice in SWE?**

Several mutually reinforcing forces prevent standardized architectural notation from taking hold across the industry. First, there is no agreed tooling: UML is the closest thing to a formal standard, but it is complex, diagram-heavy, and widely perceived as disproportionate overhead for most projects — so teams improvise with Miro boards, hand-drawn whiteboard photos, or informal box-and-arrow sketches, each using ad hoc conventions that vary by team and even by individual. Second, architectural diagrams carry a high maintenance cost with no automated enforcement mechanism: code must compile and tests must pass, but no CI check fails when a sequence diagram no longer reflects how the system actually behaves. Teams rationally stop investing in diagrams that quickly become misleading rather than helpful, because the update burden is never-ending and the penalty for skipping it is invisible in the short term.

Third, SWE lacks the professional licensing infrastructure that enforces documentation standards in civil or aeronautical engineering. There is no engineering board that mandates architectural artifacts as a condition of practice, so the discipline is entirely dependent on team culture — and culture varies enormously across organizations, projects, and countries. Fourth, architecture is often treated as the concern of a senior cohort rather than the full team, meaning most engineers never develop the habit of reading or maintaining architectural diagrams and don't see them as part of their workflow. Finally, the field moves fast enough that any particular notation or tooling choice ages quickly; committing to a standard feels risky when the landscape will look different in five years, so the investment in standardization is perpetually deferred.

## Why Requirements Documents Go Out of Date

**Q: Why do requirements diagrams and documents get out of date? How can we fight this problem? Great answers are not just technical in nature.**

Requirements documents go out of date because they are static artifacts embedded in a dynamic process, with no feedback loop that detects or punishes drift. At the moment of authoring, a requirements document represents the best shared understanding of what the system should do — but that understanding evolves continuously. Stakeholders change their minds when they see working software and realize their mental model was wrong. Market conditions shift mid-project. Technical constraints surface during implementation that force scope changes nobody anticipated. Organizational priorities pivot. In every case, the code changes and the document does not, because updating a document feels less urgent than shipping a feature or fixing a bug, and there is no hard feedback — no failing build, no broken test — that surfaces the divergence. In fast-moving Agile environments, user stories in backlogs are partially maintained but lack the broader contextual narrative a formal spec provides; in Waterfall environments, formal change control processes are so burdensome that engineers bypass them informally, and the spec drifts silently.

**Fighting it — technically:** Co-locate documentation with the code it describes so it appears in the same PR diff and gets reviewed alongside changes. Use executable specifications (BDD/Cucumber scenarios, JSDocs, or Markdown-embedded Mermaid diagrams) that must be updated when behavior changes — if the diagram is code in the repo, the PR that changes behavior must also update the diagram or it fails review. Generate diagrams automatically from running systems where possible: API documentation from OpenAPI specs, service dependency maps from observability tooling, call graphs from static analysis — so the artifact reflects the system's actual state, not a human's recollection.

**Fighting it — culturally and organizationally:** Treat requirements maintenance as a first-class engineering task with explicit time allocation and acceptance criteria, not a documentation afterthought carved from sprint margins. Assign named ownership of specific requirements sections to engineers rather than treating them as shared commons — shared ownership is effectively no ownership. Hold brief documentation-review checkpoints at sprint boundaries: "does anything we shipped this sprint contradict something written in the spec?" Recognize that the enemy of current documentation is not laziness but rational prioritization — teams update documents when they believe it matters, which means leadership must visibly treat outdated docs as a real problem rather than an acceptable norm.

## Carrying User-Centered Thinking Into Development

**Q: In the early part of the development process we spent much time thinking of users and their needs. How can we ensure that user centered thinking flows through into the later development steps of building our software? Be concrete with specific techniques if you can.**

User-centered design tends to be front-loaded: research happens at discovery, personas are created at kickoff, and then the team enters heads-down implementation and progressively loses the user's perspective with every sprint. The challenge is institutional — once engineers are in building mode, the artifact they interact with is code, not users. Specific techniques to maintain the connection:

**Persona-referenced acceptance criteria:** When writing user stories and defining done, explicitly name the persona the feature serves and ask "would this persona understand and successfully use this?" at sprint review, not just "does it work?" This embeds the user perspective into the definition of done rather than treating it as a separate UX concern.

**Usability testing at sprint boundaries:** Even a 30-minute session with two real users per sprint, watching them interact with working software, catches UX drift before it compounds. The key is making it lightweight enough to be sustainable — a quick screen-share session with a user from a customer success contact list, not a formal lab study.

**User journey maps as E2E test scaffolding:** Write end-to-end tests that follow the exact paths defined in the user journey map. This encodes the user's perspective into the automated test suite — if a journey step breaks, a test fails. It also keeps the journey map relevant to engineers, because it directly drives test coverage.

**Feature flags and behavioral analytics:** Release new features to a small cohort of real users behind a flag and instrument behavioral data — click patterns, abandonment rates, rage clicks, time-on-task. This replaces assumption-based design decisions in later sprints with actual user behavior, and surfaces usability failures that neither the design nor the implementation team could have predicted from internal review alone.

**Jobs-to-be-done framing in code review:** PR descriptions should articulate the user job being served, not just the technical change. "Adds pagination to the results table" is less useful than "Lets a user browsing many search results find a specific item without scrolling indefinitely." Framing code review this way keeps the functional human purpose of the change visible to the entire team, not just the author.

## System Model vs. User Model: Alignment and Its Signals

**Q: Explain the idea of system model and user model in software architecture. A suggestion is that the two should be aligned. What practical code or repository related "smells" would suggest that they are aligned?**

The **system model** is the internal, technical representation of how the software is organized — its modules, classes, services, data structures, and their relationships — as understood by the engineers who built it. The **user model** (or mental model) is the conceptual map a user builds in their mind about how the system works: what entities exist, what actions are possible, and what effects those actions have. When a user interacts with a system, they form a mental model based on the UI they see and the responses they receive; when that mental model accurately predicts the system's behavior, the system feels intuitive. When it doesn't, the system feels confusing, unpredictable, or broken — even if it is technically correct.

The alignment principle holds that software is most usable when its internal organization mirrors the user's conceptual model. If users think in terms of "orders" and "shipments," the system should have `Order` and `Shipment` as first-class domain objects, not internal entities named `TransactionRecord` and `FulfillmentEvent` that the UI awkwardly translates. Misalignment creates a constant translation overhead — both for the UI layer mapping between internal and user-facing concepts, and for engineers trying to understand what business concept a technical component represents.

**Code and repo smells that suggest alignment:**

- **Domain language in identifiers:** Class names, route paths, and function names use the vocabulary users and stakeholders use. A billing domain has `Invoice`, `Payment`, and `Refund` — not `BillingRecord`, `MoneyTransfer`, and `ReversalEvent`. When a product manager reads the codebase structure, they recognize their own language.
- **API endpoints read like user actions:** `POST /checkout`, `GET /orders/{id}/status` rather than `POST /transactionmanager/createrecord` or `GET /dbquery/ordertable`. The API surface reflects what users do, not how the database is structured.
- **Module/folder structure mirrors the domain:** A repo organized by business domain (`/orders`, `/inventory`, `/notifications`) rather than purely technical layers (`/controllers`, `/models`, `/views`) indicates the team thought about domain structure rather than layering by technology alone.
- **UI components map 1:1 to domain objects:** A `UserProfile` page backed by a `UserProfile` model/component/route that naturally groups the same data users perceive as "their profile" — not assembled from five unrelated database joins scattered across different services.
- **Error messages are user-meaningful:** Errors surfaced to users say "Your session has expired — please log in again" rather than exposing internal state like "NullPointerException in SessionManager:247." The system model's internal failure mode has been translated into the user model's vocabulary.
