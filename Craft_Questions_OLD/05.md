## UCD Mantra Memorization and Understanding

**Q: Be prepared to cite UCD mantras like "You are not the user" and "Don't make them wait" and explain them succinctly.**

UCD mantras are compressed heuristics designed to interrupt developer-centric thinking during design and implementation. Key mantras and their meanings:

- **"You are not the user":** Developers' mental models, technical vocabulary, and usage patterns are systematically different from those of end users. Designing from personal preference produces systems that make sense to engineers and baffle users. User research, not developer intuition, must drive design decisions.
- **"Don't make them wait":** Perceived performance is as important as actual performance. Users abandon interactions that feel slow — even brief delays erode trust and engagement. This applies to page load, API response, UI feedback, and every transition in the user experience.
- **"Fail gracefully":** When errors occur, guide the user toward resolution rather than presenting raw technical error messages or dead ends. The user should never feel the system has abandoned them.
- **"Test early, test often":** Usability problems discovered after shipping cost orders of magnitude more to fix than those caught in low-fidelity wireframe review. Cheap, early feedback is the goal.
- **"Make it visible":** Controls, affordances, and system state should be visually and semantically legible without instruction. Users should not need to discover functionality through trial and error.

## User Story Example

**Q: Write an example user story for a student using a flash card app. Be specific and use the common format for full points.**

User stories follow the format: **"As a [type of user], I want to [perform some action] so that [I achieve some goal]."**

> *As a student preparing for a midterm exam, I want to review my flashcard deck in a randomized order so that I can test my recall without relying on positional memory.*

**Acceptance criteria:**
- The app presents cards in a random sequence each session.
- The student can flip the card to reveal the answer.
- The student can mark a card as "got it" or "need more practice" after reviewing it.
- Cards marked "need more practice" appear more frequently in subsequent reviews (spaced repetition).
- The student can see a progress summary (X/Y cards mastered) at the end of each session.

## Dangerous Pretty Pixels

**Q: Why should we start with rough wireframes? What is the purpose of the roughness? What are the problems with high-fidelity prototypes early in a project?**

Rough wireframes serve a counterintuitive but critical function: their deliberate crudeness signals to stakeholders and users that the design is not final, which lowers the psychological barrier to giving honest critical feedback. When a design is polished — beautiful colors, pixel-perfect typography, refined interactions — people respond to its visual quality rather than its structural logic. They hesitate to suggest fundamental changes because it "looks done," and they focus feedback on minor aesthetic preferences rather than whether the information architecture makes sense. By contrast, a rough sketch or low-fidelity wireframe says unmistakably "this is a hypothesis, not a commitment," inviting structural critique. The purpose of the roughness is to keep attention on flow, layout, and information hierarchy — the decisions that are expensive to change later — rather than on surface aesthetics that can be adjusted trivially at any time. High-fidelity prototypes introduced early in the process are dangerous for several compounding reasons: they are expensive to produce, creating sunk-cost reluctance to discard them when feedback demands it; they attract bikeshedding (feedback concentrated on easily observed surface details rather than structural problems); and they can prematurely anchor the design direction, making alternatives feel needlessly speculative by comparison.

## Recognizing the "We Build Subsystems" Mental Model

**Q: Using the subsystem mental model (Decomposition/Execution → Form → Distribution → Environment), apply it to building a "Cringe Dad Jokes" web app that calls the OpenAI API. Give an example and a risk at each level.**

The subsystem mental model describes layers of concern from the most controllable (inner) to the least controllable (outer):

**Decomposition and Execution (Green — safest, most controllable):** This is the code itself — the functions, classes, and modules you write. *Example:* Designing the joke generation module to call the OpenAI API with a well-structured prompt, parse the response, and return a formatted joke string. *Risk:* The API response format may vary between OpenAI model versions, making brittle parsing logic a latent bug waiting for a model update to trigger it.

**Form (Yellow — less controllable):** This is how the system is assembled and presented — the UI, component structure, and the API contract between frontend and backend. *Example:* Designing the React component that displays the joke with a "Generate" button and handles loading/error states. *Risk:* If the UI assumes jokes are always short, unexpectedly long outputs from the model may break the layout or exceed display bounds without graceful truncation.

**Distribution (Orange — limited control):** How the software is delivered to users — hosting, deployment, CDN, browser compatibility. *Example:* Deploying the app on Vercel with serverless functions to proxy the OpenAI API calls (keeping the API key server-side). *Risk:* Vercel's serverless function cold-start latency may make the first joke request feel unacceptably slow, damaging the user experience on an app where instant delight is the entire point.

**Environment (Red — very limited control):** The external systems and context the software operates within — OpenAI's API availability, pricing changes, rate limits, and broader internet conditions. *Example:* Depending on OpenAI's API being available at runtime to generate every joke. *Risk:* OpenAI rate limits or outages directly break the app's core feature with no fallback, since the app has no locally stored jokes. A pre-generated joke cache or fallback bank would mitigate this environmental dependency.

## The RAIL Model

**Q: Explain the RAIL model, expand the acronym, provide the values, and explain why each value is important.**

RAIL is a user-centric performance model developed by Google that defines performance targets based on how users perceive and experience applications:

- **R — Response (0–100ms):** User interactions (button taps, input responses) should produce visible feedback within 100ms. Beyond this threshold, the interaction feels sluggish and unresponsive — users lose confidence that their action was registered. This is the hardest constraint because it covers every direct user gesture.

- **A — Animation (0–16ms per frame / 60fps):** Animations and scrolling should maintain 60 frames per second, meaning each frame must render within ~16ms. Animation below this threshold is visibly janky, breaking the illusion of fluid motion and making the UI feel cheap. This is especially critical for scroll performance on mobile devices.

- **I — Idle (50ms task chunks):** The browser's main thread should be kept free in large idle blocks, with long tasks broken into chunks of 50ms or less. This preserves responsiveness — if the main thread is monopolized by a long computation, it cannot respond to user input during that time.

- **L — Load (under 1 second for interactive on fast connections; under 5 seconds on mobile 3G):** The initial page load should reach an interactive state within 1 second on a fast connection and 5 seconds on a mid-tier mobile device. Beyond these thresholds, user abandonment rates climb sharply — research shows 53% of mobile users abandon pages that take over 3 seconds to load.

## Evaluating the User -ilities

**Q: Name the 6 user-affecting -ilities, their meanings, and provide an example of how you might verify each.**

**1. Usability:** The degree to which the system is easy to learn and use effectively for its intended users. *Verify with:* Moderated usability testing where users perform representative tasks while thinking aloud, recording where they hesitate, error, or get lost.

**2. Accessibility:** The degree to which the system is usable by people with disabilities (visual, motor, cognitive, auditory). *Verify with:* Automated accessibility scanners (axe, Lighthouse), manual screen reader testing (NVDA, VoiceOver), and keyboard-only navigation audits against WCAG 2.1 AA standards.

**3. Reliability:** The system's ability to perform its intended functions correctly and consistently without failure. *Verify with:* Error rate monitoring in production (e.g., Sentry), uptime monitoring (e.g., PagerDuty), and load testing that confirms the system degrades gracefully under stress.

**4. Performance:** The responsiveness and speed of the system from the user's perspective (see RAIL model). *Verify with:* Lighthouse performance audits, Core Web Vitals monitoring in production, and synthetic performance tests simulating various network conditions.

**5. Security:** The system's resistance to unauthorized access, data breaches, and exploitation. *Verify with:* Penetration testing, automated vulnerability scanning (OWASP ZAP, Snyk), and code review focused on input validation, authentication flows, and data handling.

**6. Scalability:** The system's ability to maintain acceptable performance as usage grows. *Verify with:* Load and stress testing with tools like k6 or Locust simulating traffic at 10x and 100x expected load, and reviewing database query plans for N+1 patterns and missing indices.

## "Spooking the Animals" and Other UCD Dangers

**Q: Explain the idea of "Spooking the Animals" and the Professor's worry and solution. Note any other examples of UCD processes going astray.**

"Spooking the animals" is an analogy for the way that user research methodologies, if handled clumsily, can disturb the very behavior they are trying to observe. The concern is that placing users in formal, sterile research contexts — a lab environment with a one-way mirror, a researcher staring intently while they use an app, being asked to narrate their thoughts constantly — makes users self-conscious, performative, and atypical. They stop behaving as they normally would and start behaving as they think a "good study participant" should, producing useless or actively misleading data. The worry is that the research method contaminates the research findings. The solution is to design observation contexts as close to natural usage as possible: field studies in real environments, diary studies where users self-report over time, analytics instrumentation that captures actual behavior passively, and A/B testing that measures real decisions rather than stated preferences. Other UCD dangers include **confirmation bias in research design** — writing survey questions or interview scripts that lead users toward the answers the team hopes to hear; **survivorship bias in user selection** — recruiting only power users or early adopters who are systematically unrepresentative of the mainstream audience; and the **difference between stated and revealed preference** — users tell you they would use a feature that they have no intention of actually using, because agreeing feels socially easier than declining in a research session.

## The T-Shaped Engineer

**Q: How does a balanced T-shaped engineer have advantages over a narrowly technical engineer in UCD contexts? If not UCD-confident, who does this work and what are the risks?**

A T-shaped engineer with genuine user-centered design literacy brings a decisive advantage at the intersection of engineering and product decisions: they can evaluate technical tradeoffs in terms of user impact rather than purely in terms of implementation elegance. When discussing API design, they ask "how will the frontend need to use this, and does this contract make that experience painful?" When reviewing a feature spec, they flag design choices that will be technically straightforward to build but confusing for users to understand. This prevents the common failure mode where technically correct systems are built that nobody can use — because the engineer who would notice user impact issues is not present in the technical discussions where those issues originate. For engineers who are not confident in UCD, the risk is not that the work goes undone, but that it is handed entirely to a product manager or UX designer who may lack the technical context to make sound tradeoffs. The result is often "design debt" — UX decisions made without understanding technical constraints, producing designs that cannot be built as specified, or worse, designs that are built but interact poorly with the underlying system architecture. The mitigation is close collaboration rather than handoffs: having UX and engineering work in parallel with frequent checkpoints rather than UX finishing "the design" before engineering starts "the build."

## AI for UCD

**Q: Discuss how AI might be useful and how it very much might not be for the UCD effort.**

AI offers genuine value in several UCD activities. AI-powered analytics tools can identify patterns in user behavior data at scales no human researcher could manually process — surfacing segments of users who struggle with a specific flow, or detecting where drop-offs cluster in a funnel. LLMs can rapidly synthesize large volumes of qualitative research data (interview transcripts, support tickets, user feedback) into themes, dramatically reducing the hours analysts spend on affinity mapping. AI can generate multiple prototype variations quickly for comparative testing, exploring a wider design space faster than a human designer working alone. Synthetic user personas generated from real data can help teams internalize user diversity without requiring constant access to live research participants.

However, AI is deeply limited in the most important parts of UCD. User research fundamentally depends on observing human behavior in context — the hesitation before clicking, the confused facial expression, the workaround a user has invented that reveals an unmet need. No current AI system can replicate the empathetic, contextually sensitive observation that skilled UX researchers perform. AI-generated "simulated users" are only as representative as the data they were trained on — they encode historical biases and cannot represent users who are underrepresented in that data, precisely the users most likely to be excluded by poorly designed systems. AI also cannot perform the interpretive, abductive reasoning that transforms raw observations into design insights: the leap from "users seem frustrated at step 3" to "the mental model the interface implies doesn't match users' actual workflow." This insight generation is where UCD's real value lies, and it remains irreducibly human.

## Accessibility for All Even Bots!?!

**Q: Explain accessibility as a range, using yourself as an example of potential needs. Can accessibility help those who don't "need" it? Can it help AI?**

Accessibility is commonly imagined as a binary — you either have a disability requiring accommodation or you don't — but it is better understood as a spectrum that intersects with context, environment, and life stage. The W3C's framework distinguishes permanent, temporary, and situational disability: a permanently deaf user, a user who is temporarily in a loud environment without headphones, and a user watching a video in a library where audio is socially inappropriate all share the same need for captions. Everyone is episodically accessible — on a bright day a low-contrast UI becomes difficult to read (situational visual impairment); with a broken arm, keyboard navigation becomes essential (temporary motor impairment); as eyes age, small text becomes difficult for everyone. Any engineer who codes for extended periods faces repetitive strain risk that makes heavy mouse use painful — accessibility features like comprehensive keyboard shortcuts are both accommodations and productivity tools.

Accessibility efforts help non-disabled users in well-documented ways: captions improve comprehension in noisy environments; high-contrast modes reduce eye strain in bright conditions; well-structured, semantically correct HTML improves navigation for power users who rely on heading structure and keyboard shortcuts. This is the "curb-cut effect" — accommodations designed for people with disabilities consistently improve the experience for the general population.

For AI, accessibility efforts are unexpectedly powerful. Screen reader accessibility requires images to have descriptive alt text, which provides structured semantic labels that computer vision systems can use. ARIA roles and semantic HTML give AI systems clear signals about page structure, element types, and content hierarchy, dramatically improving the accuracy of automated content understanding and web scraping. Well-structured, accessible documents are significantly easier for LLMs to process accurately — they present information in a logically ordered, labeled form that reduces ambiguity and hallucinated structure. In this sense, designing for accessibility simultaneously designs for machine comprehension — a convergence of human and artificial needs that makes the investment doubly valuable.
