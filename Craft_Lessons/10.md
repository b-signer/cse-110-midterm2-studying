# 10 — Building and Deving Part 1

---

## Premise

A core aspect of Agile is understanding that it is unlikely for us to know everything we need to know about a project before we start it. Unfortunately, some people use this lack of certainty as an excuse for **No Design Up Front (NoDUF)**. The proposed middle ground: do *enough* design to have explored big ideas and obvious gotchas before committing to the work — this is called **design engineering**.

Regardless of the amount of design effort employed, eventually you need to get started, and we meet the second part of software engineering process: **process engineering**, which addresses the lack of clarity we will still have. Agile proposes that we deal with that lack of clarity through **experimentation via iteration** — many small experiments over and over as quickly as we can, finding our way to success without rolling too far backward if an experiment fails.

The analogy: rolling an ever-increasing bundle up a hill, putting in a backstop as we go, and never pushing so far that the ball can flatten us.

A **build pipeline** should be created to support small-stepped, safe, experimental iteration that automates necessary tasks including quality checks (unit testing, code metrics, style enforcement) and supportive tasks (documentation generation). The build pipeline is a key idea of **CI/CD (Continuous Integration / Continuous Delivery)** — but it is not a one-size-fits-all effort. Creating this pipeline is likely contextual and should be attacked incrementally as well.

---

## Key Support Points and Ideas

### The Analogy of Rolling Complexity Up a Hill

Following Agile properly means growing software step by step. If we don't do it well, we are quite likely to create a **"big ball of mud"** — code we can't reason about.

To avoid this, visualize growing software and rolling it up a hill while backstopping it with tests and other fail-safes. This section shows how automation and the build process are key to properly applying Agile practices.

---

### The Belt Metaphor

Imagine a factory that builds a product by executing a series of automated and manual steps. Use this software factory and a conveyor belt to imagine your software being built automatically — pulling together various pieces and running various tests.

We call this process a **build pipeline**.

Build pipelines should:
- Grow to suit the type of project being run
- Not be overly complex
- Be simple enough to run that anyone on the development team can do it

---

### Formally Defining CI and CD

**CI = Continuous Integration** — Constantly being able to integrate and test software into a workable build for testing and use. CI pipelines generally have multiple steps: unit testing, linting, formatting, optimization, building/merging, documenting, and potentially more.

**CD = Continuous Delivery** — The ability to take an automatically produced build and get it out into production use quickly. This is higher risk than CI, as CI generally produces internal versions while CD promotes getting work out into end users' hands.

The frequency of build or delivery will vary based on project and risk tolerance — do not equate "always releasing" with the right approach, as it may not be for your particular case.

---

### The Benefits of Small, Safe Experiments

The benefit of building this automated build system using CI/CD thinking is that we can make small changes to our code quickly and see how we might grow.

Note the emphasis on **small and safe**: avoid "rocket launch" commits if possible. If we push small amounts of code, test it, and things don't work, it is easy enough to back out those efforts. Large pushes make rollback much harder and increase the blast radius of failure.

---

### Experimentation Can Take Many Forms — Feature Flags

CI/CD is not the only way to perform experiments on new pieces of code. The idea of a **feature toggle** or **feature flag** is also presented.

The basic sense: introduce new functionality in a system, but hide it behind some flag or conditional statement. Show this feature to a small subset of your user base and see how stable and accepted it is before rolling it out broadly.

The feature flag approach is quite common in consumer-facing internet apps for testing new ideas. However, be cautious — just as you might push too much in a CI/CD step, you might introduce too dangerous of an idea and still hurt a sizable part of your user base even within a small cohort.

---

### Incrementalism — "Feel the Hate Before You Automate"

You need to grow your pipeline step by step, solving the problem you have right now.

For example, you might do a few simple steps at first before adding more complicated ideas.

The phrase **"feel the hate before you automate"** is a reminder that at first you might want to do a step manually and understand it before deciding whether to automate it or not. Very commonly people build very complex build systems early and it turns out to be a YAGNI (You Ain't Gonna Need It) effort — a great example of **premature automation**.

---

## Conclusion

The ability to build software quickly and verify its quality is at the tool-heart of Agile. Formally we talk about automated build pipelines with the terms **CI (Continuous Integration)** and **CD (Continuous Delivery)**.

It is important to not lose the spirit of Agile just because you have automation. Try to do things in small steps, avoid premature complexity, and roll your code builder safely bit by bit rather than in big bursts — so it doesn't become a ball of mud and roll you over.
